## 1. RI-001 MCP 重构为独立软件的成熟路径与反模式
- 指向 PRD：F-001, F-011, NB-1, NB-2
- 假设陈述：从"4 个 MCP server + Claude Desktop"重构为"FastAPI + Electron / Web"是当前最稳妥的迁移路径
- 调研状态：✅ + ⚠️（RA-001 已验证）
- 关键结论：LiteLLM / Aider / Continue / Cline 中，Aider/Continue 完全替换 MCP、LiteLLM 保留 MCP 作客户端、Claude Desktop 已标准化异步 Tasks；服务端禁 MCP + 客户端 SDK 可演进是稳妥路径
- 本轮修订：**S-001**（验收改为禁 `from mcp.server`）
- **V2.0 采纳理由**：服务端禁、客户端 SDK 允许，匹配 LiteLLM 演进路线
- 待验证问题（**已闭合**）：
  1. ✅ 竞品对比已产出（详见 RA-001 §2.1）
  2. ✅ 反模式清单已收录（stdio 缓冲区、消息顺序、客户端兼容性）
  3. ✅ schema 兼容最佳实践已落地（保留 SQLite + 双后端缓存）
- 调研优先级：P0 → **✅ 已闭合**

## 3. RI-003 Python 项目打包与分发方案
- 指向 PRD：F-011, F-019, F-020
- 假设陈述：pyproject + uv + CLI 是 2026 年的最佳实践；Electron 桌面 + Web 是常见双形态
- 调研状态：✅ + ⚠️（RA-001 已验证，含风险）
- 关键结论：uv 已成熟；**PyInstaller onefile 触发 Windows Defender 误报 + CVE-2025-59042，应避免**；**Tauri 体积 2-15MB 远优于 Electron 120-250MB**；PyInstaller vs Nuitka 性能差异 2-4x
- 本轮修订：**S-004**（打包工具选 cx_Freeze/Nuitka）、**S-005**（体积目标分 Electron/Tauri）
- **V2.0 采纳理由**：CVE-2025-59042 + Windows Defender 误报避免；分形态量化体积目标
- 待验证问题（**已闭合**）：
  1. ✅ pyproject + uv 落地配置已纳入 F-019
  2. ✅ CLI 打包走 cx_Freeze/Nuitka（避 PyInstaller onefile）
  3. ✅ GUI 体积分形态量化（Electron ≤250MB / Tauri ≤50MB）
  4. ⚠️ Nuitka 商业许可待 SA-001 POC（RI-NEW-3）
- 调研优先级：P0 → **✅ 已闭合**（RI-NEW-3 待 SA-001）

## 4. **RI-004 🆕V3.0** 开发规范中红线的可执行检测方案
- 指向 PRD：**NFR-8（V3.0 强化）** / NFR-4 / NFR-9 / NFR-10
- 假设陈述：4 层工具链（**Ruff** + **Import Linter** + **Redocly CLI** + **pre-commit + CI**）可覆盖 `开发规范/conventions/` 6+1 体系的全部红线 0 红目标
- 调研状态：⚠️ **部分闭合**（V2.0 决策 Spectral → Redocly 已落地；V3.0 显式把 4 工具链矩阵化）
- 关键结论：
  - **Ruff**（替代 flake8，速度 150x）覆盖 02-代码红线（禁 print / 命名 / import 顺序）
  - **Import Linter**（合约 = Layers + Forbidden）覆盖 01-架构红线（禁循环依赖 / 领域层不依赖框架 / 禁跨层调用）
  - **Redocly CLI**（替代休眠的 Spectral，支持 OpenAPI 3.1+）覆盖 04-API 红线（命名 / 统一响应 / 默认认证）
  - **pre-commit + commitlint + GitHub Actions** 覆盖 03-Git 红线（main 禁直推 / Conventional Commits / ≥1 Approve）
  - **pytest** 覆盖率门禁覆盖 05-测试（覆盖率 ≥ 80%）
  - **双图谱（CodeGraph + Understand-Anything）** 覆盖 08-图谱（CI 自动生成）
  - **审查 + PR 模板** 覆盖 06-文档（README / CHANGELOG / 文档随码同 PR）
- 本轮修订（V3.0）：**显式将 4 工具链矩阵化**写入 NFR-8，**显式将规范红线覆盖度作为 S3 成功指标**
- **V3.0 采纳理由**：用户本轮 prompt 强约束·开发规范 = "这些红线必须可执行检测"；4 工具链是当前业界共识
- 待验证问题（**部分待 SA-001 落地**）：
  1. ⚠️ Import Linter 合约（Layers + Forbidden）具体配置范式 → SA-001 落地
  2. ⚠️ pre-commit 钩子 + commitlint 的 CI 整合方式 → SA-001 落地
  3. ⚠️ 双图谱（CodeGraph + Understand-Anything）生成器接入 CI → SA-001 落地
  4. ⚠️ Redocly CLI 对 OpenAPI 3.1+ 规范的实际 lint 规则集 → SA-001 落地
  5. ⚠️ 失败 → 修复文档（开发者友好）→ SA-001 落地
- 期望产出：CI pipeline 配置文件（`.github/workflows/redlines.yml`）+ 4 工具链的失败示例 + 修复手册
- 调研优先级：**P0**（V3.0 提升，因规范红线覆盖度是 G3 核心）
