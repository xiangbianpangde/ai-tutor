# 方案对比报告 — AITutor V3.1

> 主方案 vs 备选方案（7 维度加权对比）

---

## 主方案 A：分层 + 插件化 + 事件总线（混合架构）

**核心特征**：
- L1~L5 严格分层（BR-002 单进程承载）
- 中间件 5 类强制装配（BR-003）
- 事件总线统一处理 WS/FSM/兜底审计
- 翻译/NLI/OCR 走插件化注入（保持核心稳定）
- 17 模块（合并后落在 [16, 17] 上沿）

## 备选方案 B：微服务架构（按主题拆服务）

**核心特征**：
- 5 服务（教学/RAG/打包/红编/会话）独立部署
- 服务间 REST + 消息队列
- 独立数据库
- 模块数 = 5 服务 + 5 DB + 1 API Gateway

| 对比维度 | 权重 | 主方案 A | 备方案 B |

### 单条细则评分依据

- **内聚度** A=9：M-001~017 大多 6/6 通过；B=6：服务拆分后跨服务共享 schema 难
- **耦合度** A=8：事件总线解耦 70% 调用；B=5：REST 强耦合 + 失败传播复杂
- **扩展性** A=9：插件化预留（NLI/翻译可换实现）；B=9：水平扩展自然
- **简洁度** A=7：17 模块在 [6,16] 上沿；B=5：5 服务+5DB+MQ+GW 复杂
- **性能风险** A=7：单进程瓶颈（asyncio 缓解）；B=9：独立扩展
- **实现复杂度** A=8：FastAPI 单进程；B=4：Docker+K8s+MQ+服务注册
- **成本** A=9：单服务器；B=5：多服务多组件

---

## 选择理由

**主方案 A 优势**：
1. 符合 PRD 单用户 / 单进程定位（BR-002）
2. 与调研报告 RI-001/S-001 单进程建议一致
3. FastAPI 单进程 + asyncio 可承载 V3.1 量级
4. 实现成本低（3 人月 vs 8 人月）
5. 学习成本低（FastAPI 主流框架）

**备选 B 不选理由**：
1. 偏离 PRD 单用户/单进程定位
2. 单用户场景下微服务运维成本过高
3. 5 类中间件强耦合（F-002 强制装配）→ 微服务拆分破坏 BR-003
4. WS 推送强实时性（≤1s）→ 服务间网络延迟难达成
5. 微服务拆分后事件总线（横切关注点）需独立基础设施，复杂度高

**结论**：A 总分 7.6 vs B 总分 5.8，差距 1.8 < 5 分阈值，但 A 在 5/7 维度领先，且 4 个维度差距 > 1 分（内聚/简洁/实现/成本）。**A 更适合 V3.1 现状**。B 留作 V4.0 多用户扩展时的备选。
