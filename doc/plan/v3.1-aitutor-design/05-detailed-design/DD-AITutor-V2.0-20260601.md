### 1.1 范围
将 AR-001 的技术方案细化为可直接交付 DD-M 实施的详细设计规范，涵盖：
- 10 个模块（M-001~M-010）的子模块/类/函数/状态机/异常/日志/测试 7 项细化

### 1.2 原则
- **可落地**：每条规范都能被开发直接遵循，不留模糊表述

## 五、设计模式选择（soul 4.8）

### 5.1 核心模式与匹配分析

| 模块 | 选定模式 | 备选模式 | 选择理由 |
|------|---------|---------|---------|
| M-001 | Bootstrap + Chain of Responsibility（中间件链） | DI 容器（未引入） | FastAPI Depends 注入天然支持中间件链；不引入额外容器 |
| M-002 | Strategy（5 教学子策略）+ State Machine（learner 阶段） | 单一类大方法 | 5 策略职责清晰，可独立测试；状态机保证状态转换可复现 |
| M-003 | Chain of Responsibility（NLI→SLM→LLM 三级级联）+ Circuit Breaker | 单一裁决类 | 三级级联是天然责任链；Circuit Breaker 保护 LLM 调用 |
| M-004 | Pipeline（5 步流转）+ Repository（持久化） | 单体大函数 | 5 步流程清晰可中断可恢复；Repository 隔离存储差异 |
| M-005 | State Machine（LangGraph StateGraph）+ Strategy（rerank/llm） | 自研 FSM | 编排可观测；max_total_rounds=5 由 ADR-005 强制 |
| M-006 | Repository（SQLite）+ Cache-Aside（Redis/LRU） | 直接 SQL | 跨会话记忆需可查询；Cache-Aside 提升热路径性能 |
| M-007 | Adapter（3 LLM Provider）+ Token Bucket（限流） | 直接 if-else | 适配器隔离 SDK 差异；Token Bucket 防止 provider 限流 |
| M-008 | Finite State Machine（自研 transitions）+ Observer（FSM 变更广播） | LangGraph | BR-020 要求可复现版本化；自研 FSM 确定性更强 |
| M-009 | Observer（事件总线）+ Heartbeat | 直接 WebSocket | 推送解耦；Heartbeat 维持连接 |
| M-010 | Adapter（3 出口）+ Entry Point（CLI 插件） | if-else | 适配器隔离 Anki/Obsidian/Plugin 差异；Entry Point 标准化插件加载 |

### 5.2 设计模式一致性约束（R22）

| 模式 | 模块设计规则 | 接口设计规则 | 文件组织规则 |
|------|------------|------------|------------|
| Repository | 每个实体对应一个 Repository 类 | Repository 接口统一 CRUD | repositories/ |
| Strategy | 策略接口统一（execute + 上下文） | 上下文对象包含全部必要数据 | strategies/ |
| State Machine | 状态转换表完整且不可逆即终止 | 状态查询接口只读 | states/ |
| Adapter | 适配器不修改原始语义 | 适配器接口与目标接口一致 | adapters/ |
| Chain of Responsibility | 每级可独立降级 | 降级事件上报 Monitor | chains/ |
| Pipeline | 每步可中断可恢复 | 步进状态可查询 | pipelines/ |
| Observer | 事件 schema 稳定 | 订阅/退订接口统一 | events/ |

## 七、DD 洞察（≥1 条/轮，本轮 3 条）

### [DD-洞察-001] IC-005 FSRS 调度的"AGAIN 风暴"需客户端退避
API-005/IC-005 `POST /v1/pedagogy/fsrs/schedule` 接受 grade=1（AGAIN）时，会立即把 `card.due` 置为 now+10min（FSRS v4 默认）。如果用户连续点 AGAIN，5 分钟内可能产生 50+ 次重排（[AR:ADR-006]）。当前 AR 规范"5min/卡 1 次"是**服务端侧**的硬限制，但客户端若不感知，可能在 UI 上仍可点击，造成"已发送但被服务端拒绝"的困惑。**设计建议**：在 IC-005 出参增加 `retry_after` 字段（429 时告知客户端下次允许的 ISO 时间），前端做按钮 disabled+倒计时。[DD推断:基于 ADR-006 与典型 FSRS 客户端 UX]

### [DD-洞察-002] IC-013 RAG 编排的"trace_id 透传"必须穿透 LangGraph StateGraph
API-013/IC-013 `POST /v1/rag/query` 的 trace_id 在 AG-005 内部必须穿透 LangGraph StateGraph 的所有节点（preprocess→retrieve→rerank→llm→postprocess）。如果仅在入口注入而不在 StateGraph 节点间传递，会出现"trace_id 在 span 内丢失"的可观测性盲区。**设计建议**：M-005 在 StateGraph 的 `config={"callbacks": [OTelSpanHandler]}` 中显式注册 OTel callback，确保每个节点 span 都带 trace_id。[DD推断:基于 AR §三 OTel + [SA:BR-004]]

### [DD-洞察-003] IC-019 LLM Provider 切换的"冷启动延迟"未在性能约束中体现
API-019~021/IC-019~021 的 LLM 调用 30s 超时 + 1 次重试（[AR:EX-009/034]）未考虑**冷启动延迟**：Claude Haiku 4.5 首次调用的 TLS 握手 + DNS 解析 + 模型预热可达 1.5~2.5s（[调研报告:NLI-12]），会直接拉低 P50 体验。**设计建议**：M-007 在 DP-002 启动后第 30s 触发一次"预热 ping"（不计费 token），把首调用延迟从 2.5s 降至 0.8s。[DD推断:基于 [调研报告:NLI-12] + 典型 LLM SDK 冷启动经验]
