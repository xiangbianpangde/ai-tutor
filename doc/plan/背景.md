# 项目背景：AI-Tutor 重构为独立桌面应用

> 流程档位: 标准
> 收束节点: 功能点3后 / 功能点6后 / 功能点9后

## 项目定位

将当前"4 个 MCP Server + Claude Desktop"的 AI 辅导系统重构为**独立 Electron 桌面应用**，用户直接打开软件即可使用，无需任何外部依赖。保留现有 7 层认知架构和核心教学能力，但彻底改变交付形态。

## 当前问题

### 架构层面

1. **强依赖 Claude Desktop**（问题 #4, #21）：4 个 MCP server 通过 stdio/SSE 挂载到 MCP Host，无法独立运行。人 → AI(Claude) → ai-tutor 多了一层中转。
2. **MCP 协议在复杂交互中不可靠**（#4）：多轮教学对话时调用失败，最终"直接放弃使用mcp"。
3. **无独立会话管理**（#6）：不支持切换会话，长时间使用 token 消耗越来越大，无长期记忆、无会话总结。
4. **文件结构混乱**（#5）：data/ 下几十个 UUID 目录，无法清晰管理。

### 数据管线层面

5. **无调研工具**（#1）：简单的爬取信息，没有清洗、整理，格式混乱。
6. **检索质量差**（#9）：一次检索覆盖面不足（45% 覆盖率），缺少 Agentic RAG 的深入检索（可达 70-80%）。
7. **调研无法用本地资料**（#14）：只能线上搜，不支持本地文件作为检索源。
8. **缺少缓存/监控层**（#11）：常见问题每次都搜，没有质量追踪。

### 交互体验层面

9. **可视化等于无**（#3）：只有一个简陋 HTML dashboard，无知识图谱可视化、无遗忘曲线图。
10. **降阶法第一阶段要读 5 万多行 MD**（#2）：没有分页/摘要，直接扔全文。
11. **无休息提醒**（#10）：缺少学习时长检测→自动建议休息。
12. **费曼学习法未完整实现**（#12）：`feynman.py` 只有精简状态机。
13. **阶段过渡太猛**（#16）：Phase 1.0→2.0 无缓冲。

### 模型/集成层面

14. **长期使用后出现强幻觉**（#18）：缺少事实核查机制。
15. **pdf2zh 结合度差**（#19）：PDF 转中文流程不稳定。
16. **AI 凭理解运行引擎**（#20）：缺少规则约束层兜底。

## 设计决策

### 为什么是 Electron 而非纯 Web

- **离线优先**：核心教学逻辑（BKT/拓扑排序/遗忘曲线）纯本地计算，LLM 仅在需要时调 API
- **本地文件访问**：需读取 PDF/Markdown/Obsidian vault，浏览器沙箱受限
- **单用户桌面场景**：不需要多租户、不需要服务端部署

### 为什么保留 Python 后端

- 现有 60+ 文件、672 测试的 Python 代码经过多轮审查，质量可靠
- 科学计算依赖（numpy/scipy/networkx）Python 生态远优于 Node.js
- BKT/遗忘曲线拟合/DKT 等算法重写成本高、风险大

### 为什么取消 MCP 而非修复 MCP

- MCP 设计初衷是"工具调用"，不是"持续多轮教学对话"
- 教学需要双向实时通信（学生作答→即时反馈），MCP 的 request/response 模型不适合
- 取消 MCP 后可直接用 WebSocket 做实时通信，FastAPI REST 做指令下发

### 为什么统一后端而非保留 4 个独立 Server

- 当前 4 个 MCP server 彼此独立，通过 SQLite 共享状态——实际已经是"逻辑单体"
- 合并为单一 FastAPI 应用可消除跨进程通信开销，简化部署
- 内部仍按模块分层（knowledge/tutoring/digest/sync），保持代码边界清晰

## 现状

- 核心教学循环已跑通：冷启动→学→评→诊断→策略推进→心流→复习计划
- 4 个 MCP server · 32 个 tool · 672 测试全绿
- 关键缺失：DKT/画像演化/学生知识网络/多源融合/12→3 语义关系
- 当前仅能通过 Claude Desktop 使用
