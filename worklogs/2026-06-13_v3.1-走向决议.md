   拆分"的既有处置；v1 已有先例（翻译能力独立成 md_translator 单模块），C3 波验收
   追加：M-008 四子能力（RAG/NLI/索引/翻译）各自独立可测。

## 三、A2 · 走向决议：选 **C'**（修正版 C），否决 A/B/D 的理由

### 否决 A（纯按 v2 11 功能点推进，不采 v3.1）
1. v2 有三个**已被调研证伪或完全空白**的点位：① 打包文档用 PyInstaller spec，而
   R-01（CVE-2025-59042 + Defender 误报）明确 onefile 不可用，须 Nuitka/cx_Freeze
   onedir——选 A = 明知设计已被推翻仍照旧开工；② 规范红线 0 红（用户强约束 6+1）
   在 v2 全部文档中**无任何落点**，M-016 是唯一承载；③ 模块间解耦通信（事件总线）
   v2 假设同步调用，#7 status 推送/#11 监控埋点没有统一事件层。
2. #10 策略升级在 v2 是单功能点"一锅炖"——这正是 v1 七策略五个烂尾（精简状态机）
   的结构性根因；v3.1 拆成 6 个可独立交付的模块直接对症。

### 否决 B（纯按 v3.1 17 模块推进，弃 v2 文档）
1. v3.1 框架代码骨架是为全新 `src/aitutor/` 仓库设计的（M-014 FDR 引用
   `aitutor.shared.exceptions`、`storage.UnitOfWork`），完全绕开 v1 现存资产
   ——shared/ 60+ Pydantic 模型、4 server 32 tool、792 条测试基线全部作废重写，
   违背核心规则 4/5（SQLite schema 兼容、测试保持通过）。
2. v3.1 的"零修改走通"验证主线是视频调研——v1 现实最薄弱路径（段七保留项）；
   把全部计划资产押在一套未经 v1 现实校准、且收敛指数为自评的设计上，风险最大。
3. 11 份 BDD 规格全部按 v2 功能点组织，选 B 还要重写验收体系。

### 否决 D（v3.1 全面替代 v2，重做 v2 文档）
D = B 的全部代价，再加把 10 份 v2 设计文档重写为 v3.1 形态。而 v2 文档刚在 06-12
根因调查中被验收红线强化过（22 问题 ↔ 功能点映射经过实测取证）——为对齐一套自评
指标扔掉经过实战校准的计划资产，成本收益完全倒挂。

### 选 C' 的内容
- **v2 主体推进**（10 份 design/ + 11 份 BDD 不动，迁移而非重写）；
- **v3.1 三个新模块作为增量**：M-006 事件总线 / M-015 打包调度（Nuitka onedir）/
  M-016 红线编排（6+1 矩阵 + CI 阻断）；
- **#10 按 v3.1 拆 6 模块实施**（M-009~M-013 + M-016），BDD specs/10 保持验收口径；
- **技术栈显式化采纳**：FastAPI 0.115 / Python 3.11 / uv 锁版本 / LangGraph 1.0
  （M-008 落地时）/ HaluGate 级联（RI-NEW-1 实测后定级数）；
- **加 §五的 6 项修正**（与原 C 的差异所在，也是本次 review 的增值）。
